# F-506 checkout result handoff

The successful `/checkout` flow now renders `CheckoutResult`: a server-valued group summary, one card per seller/order, individual status checks against `GET /api/v1/orders/{id}`, and a keyboard-accessible refresh action. The server group total is displayed unchanged. F-602 adds a count of orders whose latest confirmed status is PAID or a later fulfillment state; this count does not mutate the backend checkout status or calculate financial totals. Each response must match the requested order, checkout group, seller and current buyer before it becomes usable. Separate sellers remain independent when one order is paid or one lookup fails.

Order details remain in the in-memory QueryClient only while the result is mounted (`gcTime: 0`); requests consume cancellation signals. Query keys are scoped to the buyer and group, and F-505 clears result state on account/token changes. Private API responses are already NetworkOnly in the built worker. Offline output is explicitly the last confirmation and disables payment; it refreshes after reconnect. The success heading receives focus on entry. English and Amharic use selected language → Amharic → English.

## Remaining integration blockers

1. The live OpenAPI on 2026-10-18 has no reservation deadline in `CheckoutResponse` or `OrderDetailResponse`, and no reservation-read endpoint. The production result shows an unknown deadline. Do not derive it from `createdAt` or invent an `expiresAt` DTO property. The backend must expose an authoritative per-order deadline, then regenerate the types and wire it into `ReservationCountdown`.
2. `ReservationCountdown` is implemented and tested for explicit timezone-bearing deadlines, changing device time/suspended tabs, elapsed time and server-confirmed expiry. Local elapsed time asks for a server refresh rather than asserting reservation release. The current backend can report cancellation because of expiry through `statusHistories`; the result recognizes its exact server reason only when the current order status is `CANCELLED`. Ordinary cancellations are not called expired. The backend scheduler is a separate known issue; this frontend does not release reservations.
3. Resolved by F-602 (`ed05fa1`): verified online PLACED orders now open the existing F-601 Telebirr modal directly with their fresh server amount and currency. The unused `paymentHref` route handoff was removed. Each modal targets one order and has its own buyer/target-scoped attempt key. A verified settlement only refetches that order; it never marks the other sellers or the group paid. Missing/invalid totals, offline/auth changes, failed verification and cancellation disable or close the action. Group progress in English/Amharic distinguishes partial payment and uncertain/outdated status. No new endpoint or financial group status is invented.

The checkout result stays in the current application session, as in F-505; forced reload recovery/history belongs to a future API/history integration. No private result is persisted. MSW returns generated `OrderDetailResponse` fixtures only after the same demo account has completed the supported honey checkout. Browser expiry checks simulate a typed server cancellation response; they do not prove live scheduler operation.

F-506 remains `[!]` until the authoritative deadline contract is available. Payment wiring is delivered in F-602 on `integration/four-agent-baseline` / `ed05fa1`. Verification: 549 frontend tests, typecheck/lint/build, and a Firefox 360 px keyboard fixture pass. The fixture confirms two independent payments, 1/2 then 2/2 progress, distinct keys/amounts, no overflow and zero checkout axe violations; it does not prove real provider settlement.
