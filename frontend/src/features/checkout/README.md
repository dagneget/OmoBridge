# Checkout (F-505)

`CheckoutForm` is rendered by the thin, authenticated `CheckoutPage`. The page verifies a stored session on direct visits because the integration base does not start auth bootstrap centrally. All authenticated roles match `BuyerOrderController`'s `isAuthenticated()` policy; backend authorization remains authoritative.

The generated `CheckoutRequest` is posted to `POST /api/v1/checkout`. Its body contains a new UUID idempotency key, validated product IDs and quantities from the cart, delivery address, normalized Ethiopian mobile number, optional notes and optional coordinate pair. No prices, totals or seller IDs are submitted. Fresh network cart checks run before a new submission; all-or-nothing reservation and final amounts belong to the backend.

`useCheckoutStore` permits one pending action. Ambiguous network/5xx/incomplete-response failures retain an immutable payload and key, lock delivery editing, and offer an explicit retry. A 409 conflict also keeps the original key until the backend can reconcile it. Retry survives route unmount/remount in the current app session. Definite 400/403/404/422 rejection permits a corrected action and new key, retaining the cart and refreshing individual checks. Stock errors are shown per item from fresh product responses; backend stock errors currently lack structured product IDs, so an unrepeatable stock race may show only the generic rejection.

Only a complete response with exactly one unique order per expected seller is confirmed. Displayed money comes directly from that response. Confirmation clears the submitted cart only when its intent still matches; concurrent cart edits are retained. Account/token changes reset checkout state, and stale responses cannot publish into a new session. Delivery data and private responses are not persisted to browser storage. A before-unload prompt discourages losing a pending/ambiguous action: a forced reload closes that in-memory retry session. Cross-reload recovery needs a backend lookup/reconciliation contract and is not claimed here.

The lazy Leaflet picker uses a circle pin with translated 44 px zoom controls. Latitude/longitude fields provide a complete keyboard alternative; both coordinates must be supplied together and within geographic bounds. Map tile failures preserve the coordinate form. English/Amharic strings use selected language → Amharic → English.

MSW has a deliberately fixed, generated-type fixture: one honey unit (`ffffffff-ffff-4fff-8fff-000000000001`, quantity `1`) creates one seller order with a server-fixture total of 470 ETB. Other carts explicitly return 422 in demo mode; no general mock pricing engine or real payment is implied. The actual API accepts arbitrary validated carts. F-506 will add the reservation countdown and per-order payment navigation.

Verification: checkout UI, service and mock tests cover fresh stock, stock races, duplicates, immutable retries, malformed/partial confirmations, multiple sellers, tampering, delivery validation, offline behavior, session verification and logout. Built-worker routing covers checkout GET/POST NetworkOnly. Browser checks use MSW, not real financial transactions.
