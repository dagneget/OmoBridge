### What the runnable suite actually proves

It drives the production code path — `ProviderJobDetailPage` → `useLocationCapture` →
`createLocationCapture` → `createMemoryLocationQueue` → `syncJobLocations` →
`deliveryService.ingestLocations` — and reads the **real axios request bodies** via the
`httpClient.defaults.adapter` stub that `httpClient.test.ts` already uses in this repo. It covers:

- fixes enqueued **out of order while offline** are uploaded in `recordedAt` order on reconnect;
- a large backlog splits into 50/50/20 and the server still receives it chronologically;
- nothing is sent while offline, and the screen does not claim the job is missing;
- a 5xx leaves the point queued and it is replayed identically on the next attempt;
- the server's `stored: 0` discards the points and is not retried;
- captured points appear as "waiting to upload" on the screen.

What it does **not** cover, because jsdom cannot: a genuine `context.setOffline`, real IndexedDB,
and service-worker behaviour. That is exactly what the Playwright spec adds, and it is the gap
`[!]` is recording.

## Bug found and fixed while writing this

`ingestLocations` returned `res.data?.data ?? 0`. Since `syncJobLocations` reads `0` as "the job
is finished server-side, discard those points", **any 200 response with a missing `data` field
would have silently destroyed a provider's queued location history.** It now throws when the
count is not a number, so a malformed response keeps the points for retry. Covered by the
retry test.

A second, smaller issue: the queued-point count said "N points recorded" while the points were
actually waiting to upload. Corrected in both locales, with the F-1103 assertions updated.
