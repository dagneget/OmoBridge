## Backend endpoints used (from the live OpenAPI contract)

| Method | Path | Use |
|---|---|---|
| GET | `/api/v1/delivery/providers/{providerId}/jobs` | Resolves the job. **There is no single-job GET for providers**, so the detail view looks the job up in the provider's own list. A `jobId` outside that list renders "not found". |

## Valid next steps

`DeliveryStatus.canTransitionTo` is mirrored in `deliveryStatus.ts` because the backend does not
publish the legal set in a response:

```
PENDING    -> ASSIGNED | CANCELLED
ASSIGNED   -> PICKED_UP | FAILED | CANCELLED
PICKED_UP  -> IN_TRANSIT | FAILED | CANCELLED
IN_TRANSIT -> DELIVERED | FAILED | CANCELLED
DELIVERED / FAILED / CANCELLED -> terminal
```

`PENDING -> ASSIGNED` is deliberately not offered: assignment is a dispatcher action.
The mirror only avoids showing a button the server will refuse. The server stays authoritative —
a rejection is surfaced with its message, and the screen re-reads the job so it shows where the
job actually is. **If the backend enum changes, update the table in the same commit.**

## States covered

Loading · empty/no-match · error + retry · 403 (permissions wording) · offline · success · rejection.

Notable: when offline with nothing cached the screen says it cannot load, and **never** claims the
job is missing. When offline with a cached job it keeps the job visible and disables the actions.

## Test-infrastructure trap worth knowing

Dispatching `window.dispatchEvent(new Event('offline'))` in a test flips React Query's
process-wide `onlineManager`, which silently **pauses** every later query in the run
(`fetchStatus: 'paused'` while `enabled` is `true`, no request sent). Both provider suites now
dispatch `online` in `afterEach`. Recorded in `AGENTS.md` so the other agents do not lose time to it.
