## Design decisions worth reviewing

**Throttling, because `watchPosition` has no interval.** The browser delivers a fix as soon as
the GPS chip produces one — several per second while stationary. Accepted fixes are throttled to
one per `intervalMs` (30 s) and `enableHighAccuracy` is left off. This is the battery requirement
made concrete: a chip pinned in high-accuracy mode is the difference between a battery that lasts
the shift and one that does not on low-end Android.

**`recordedAt` is the device clock.** The backend sorts a replayed batch on
`LocationIngestionRequest::recordedAt` (`DeliveryService.ingestLocations`), so a late offline
upload still lands in the order the route was actually travelled. Using the receive time would
flatten the breadcrumb.

**Points are validated client-side.** Non-finite and out-of-range coordinates are dropped, a
repeated fix the browser replays is ignored, and a fix implying more than ~200 km/h since the
last accepted one is discarded as a GPS jump. This keeps garbage out of F-1104's queue, which
would otherwise have no way to tell a real detour from a bad fix.

**"Stop after delivery" is structural.** Capture is gated on `isActiveStatus(job.status)`; when the
status becomes terminal the caller stops passing `true` and the watch is torn down. There is no
separate stop condition that could disagree with the job's real state.

**Permission and wake lock are best-effort.** `navigator.permissions.query('geolocation')` is used
only as a hint and is absent in several browsers, so `unknown` is a real state. The actual prompt
comes from `geolocation.watchPosition`. Wake-lock failure is swallowed deliberately — it must never
block capture. F-1108 explains this to the user.

## Scope boundary

Points are held **in memory only**. IndexedDB persistence, batched upload in reverse order, clearing
after success, and the "job already delivered" replay case are all **F-1104**, and were deliberately
not started here.

F-1103: 21 new tests. Engine tests drive a fake geolocation that hands back a watch id and lets the
test push fixes, and cover device timestamps, clock fallback, omitted `speed`, the low-accuracy
options, throttling, replayed fixes, impossible jumps, invalid coordinates, double start/stop, and
error codes. Screen tests use a mocked `navigator.geolocation` and assert opt-in-only capture,
start/stop, stop-on-terminal-status, no capture control on a closed job, denied permission vs
unavailable GPS, offline, and that a rejected status change does not disturb capture.

**360 px / keyboard / a11y:** no fixed widths or `overflow-x-auto`; capture controls are real
`<button type="button">` with visible text labels and `aria-hidden` icons; the tracking badge is a
`role="status"` and both error banners are `role="alert"`.
