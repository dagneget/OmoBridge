## Endpoints used

None directly. The screen calls the existing queue/sync modules, which already own the requests:

- `PATCH /api/v1/delivery/jobs/{jobId}/status` — via `syncJobStatuses`
- `POST /api/v1/delivery/jobs/{jobId}/locations` — via `syncJobLocations`

Both are invoked only when the provider asks. **Nothing is sent on mount.**

## The one decision worth reviewing

**Discarding a status change takes everything queued after it, and says so first.**

`syncJobStatuses` replays queued changes oldest-first against the job's live server state,
because the backend only accepts a transition legal from where the job actually is. Dropping an
early change therefore makes every later one replay from a state it was never meant to follow —
`PICKED_UP` discarded, so `DELIVERED` is offered while the server still has the job `ASSIGNED`.
The backend refuses that, and `syncJobStatuses` treats a refusal as final: it removes the change
and surfaces the server's message, on the grounds that a refused transition can never become
valid later.

So discarding one change would silently discard the ones behind it too. They are removed
together, in one confirmed step, and the dialog states the count. Discarding location points does
not cascade — each fix is independent, so they go as a whole without that warning.

`statusChangesDiscardedWith(entries, id)` is the rule, tested on its own. It returns `[]` for an
id that is not in the list, so a stale copy of the queue cannot discard anything by accident.

## Behaviour worth knowing

- **No sync on mount.** Opening the screen with a large queue would otherwise fire requests the
  provider never asked for. The screen reports; the provider decides.
- **Sending while offline is refused up front**, not attempted and failed. A guaranteed failure
  carries no information, and the provider would lose the difference between "the server said no"
  and "there was no server". Offline is a state with its own message, not an error.
- **A failed queue read shows an error state, not an empty one.** Showing a clean slate when
  storage could not be read would tell the provider their queued work is gone.
- **A server refusal surfaces the server's own words.** A refusal means the device has been
  acting on a stale view — usually a dispatcher or the SMS checkpoint moved the job while it was
  offline — so the message is shown rather than reduced to "an error occurred".
- `usePendingSyncCount` only polls **while the count is above zero**, and stops the moment the
  queue drains. It is mounted in the dashboard layout for every screen a provider visits, so a
  permanent interval would be a background cost for a badge that would read zero either way.

## Shared-file patch for Codex

### 1. `frontend/src/routes/index.tsx` — required

Add the lazy import next to the existing delivery ones (after line 57):

```tsx
const PendingSyncPage = lazy(() => import('../pages/dashboard/delivery/PendingSyncPage'));
```

Add this route **before** `/dashboard/delivery/*`, which would otherwise match it first:

```tsx
<Route
  path="/dashboard/delivery/sync"
  element={
    <RoleGuard allowedRoles={[Roles.DELIVERY_PROVIDER, Roles.SYSTEM_ADMIN]}>
      <PendingSyncPage />
    </RoleGuard>
  }
/>
```

### 2. `frontend/src/components/layout/DashboardLayout.tsx` — the badge

The nav item is already there. Add the count and a badge field:

```tsx
import { usePendingSyncCount } from '../features/delivery';

// inside the component
const pendingCount = usePendingSyncCount();
```

Widen the nav item type with an optional `badge?: number`, and pass it on the delivery entry:

```tsx
{ to: '/dashboard/delivery/sync', label: 'Offline Sync Queue', icon: CheckCircle, badge: pendingCount ?? undefined },
```

Render it inside the existing `NavLink`, after `<span>{label}</span>`:

```tsx
{badge ? (
  <span
    aria-label={`${badge} waiting to sync`}
    className="ml-auto min-w-5 h-5 px-1.5 rounded-full bg-amber-500 text-white text-[11px] font-semibold flex items-center justify-center"
  >
    {badge > 99 ? '99+' : badge}
  </span>
) : null}
```

The count is exposed through the feature barrel (`features/delivery`), so the layout imports it
from there rather than reaching into a module.
