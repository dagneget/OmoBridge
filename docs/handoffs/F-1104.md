## Behaviour derived from reading the backend, not assumed

Three facts in `DeliveryService.ingestLocations` drove the design:

1. **It stores every point it is given and returns that count** — it never dedupes. So a batch
   that comes back non-zero is safe to delete from the queue.
2. **For a DELIVERED or CANCELLED job it returns `0` with HTTP 200**, storing nothing, and logs
   "ignoring location updates". That is not an error. Because of (1), a non-empty batch that
   yields `0` can only mean the job is finished server-side, so those points are **dropped** and
   the job is marked finished. Without this the queue would retry them forever and never drain.
   The server's answer wins over the local status because a job can be finished by a dispatcher
   or by the SMS checkpoint fallback while this device is offline.
3. **There is no server-side rate limiter and no size cap** — `@NotEmpty` is the only constraint
   on the batch. The 50-point cap is the client's, per the plan's backend-gap table. A long
   offline stretch would otherwise accumulate thousands of fixes into one request.

Batching is capped at 50 and order is preserved across batches. Ordering is by `recordedAt`, the
device timestamp, because the backend sorts on it.

## Test coverage — and one honest gap

15 tests cover ordering (including out-of-order enqueue and timestamp ties), batch capping and
preservation, payload shaping, the offline→reconnect→ordered-upload scenario the task requires,
mid-sync failure keeping only the un-sent batches, the `stored === 0` terminal case including
"does not retry forever", and multi-job isolation.

**Gap:** the IndexedDB adapter itself is **not** covered by an automated test. jsdom does not
implement IndexedDB, and covering it would need `fake-indexeddb`, which means adding a
devDependency — a `package.json` / lock change that is Codex-owned. The adapter is therefore
exercised only by typecheck and by the memory-fallback path. What *is* tested is everything that
carries behaviour: the queue interface, ordering, batching, and the sync loop. The IndexedDB
adapter's job is to satisfy that same interface.

**Requested from Codex:** add `fake-indexeddb` to devDependencies so
`createIdbLocationQueue` can be tested directly. Until then `createIdbLocationQueue` falls back to
the in-memory queue when `indexedDB` is absent, which also covers private-browsing browsers.
